Added
~~~~~
- Utils: ``gimdict`` is a ``MutableMapping`` in full, as its registration says (D66): ``keys()``, ``values()`` and ``items()`` (live views), ``pop``, ``popitem``, ``clear`` (the strategies stay), ``setdefault``, ``update`` (it sets, as ``d[key] = value`` does; merging is ``merge_in`` and ``|``), ``==`` with any mapping of the same items (the strategies are not compared; unhashable, as dict), ``reversed()`` and a repr of its items. Held to dict call by call (``tests/unittests/test_gimdict.py``). Example: ``docs/examples/utils/example_03_gimdict.py``.
- Benchmarks: ``benchmarks/pathset_read.py`` times ``PathSet.read_each()`` and ``read_all_files()`` against Python's ``open().read()`` loop, warm and (``--cold``) with the pages dropped, and a ``**`` glob against pathlib's, over ``--root`` or 20,000 generated files: the end-to-end rows of ``docs/design/pathset_storage.md``.
- Build: ``PYGIM_SANITIZE=address,undefined`` (or ``thread``) builds instrumented extensions; ``tests/static/run_tests_under_sanitizers.py`` builds a copy of the working tree so and runs Python tests against it, as many compiles at once as the free memory holds.

  Settled before it shipped:

  - ``run_sanitizer_hunt.py`` with no roots stops with a usage error instead of spinning for ever.
- Utils: ``pygim.utils.cpu()`` is this machine's processor as pygim's kernels see it: the data caches in bytes as one core sees them (``l1d``, ``l2``, ``l3`` the last level; a size the system does not report is a typical one, never 0), the cache ``line``, and whether ``avx2`` kernels may run. Read once from the system (Linux sysconf then /sys, macOS sysctl, Windows GetLogicalProcessorInformationEx; CPUID for AVX2). C++: ``utils/cpu.h`` (``this_cpu()``, ``cache_layout``), which sizes similarity's stream tiles. Strategy: ``docs/design/vectorisation.md`` ("Caches").

  Settled before it shipped:

  - ``pygim.utils.cpu()`` read a cache's type from the first byte of its size where the kernel's ``/sys`` list is the source (glibc on arm64, musl), so an L1 instruction cache larger than the L1d stood as the L1d; the list is now read as ``type``, and the choice is a ``constexpr`` function proved on such a list.
- Similarity (``pygim.similarity``): deterministic structural similarity of functions, methods and classes, compared all against all within ONE language — Python with Python, C++ with C++, never across. ``Index(language)`` collects units (``add(source, origin)``, ``add_file(path)``; ``units()`` is a ``pyarrow.Table`` too); ``pairs(kind, threshold, min_size)`` returns a ``pyarrow.Table`` (built in C++ with the GIL released, handed over through the Arrow PyCapsule protocol without a copy; unit ids join ``units()``, file names dictionary-encoded) that scores every combination of functions (methods included) or of classes with the Dice coefficient over Merkle-hashed subtrees of the normalised syntax tree (each subtree of two or more nodes counted once, leaves left out: one edit costs only the subtrees around it, so near-duplicates score ~0.85 while unrelated code stays near 0.05 — measured on 600 mutated stdlib functions, ``docs/design/similarity.md``) (locals renamed by first appearance; docstrings, annotations and literal values dropped; globals, attributes and calls kept), reported as the exact ratio ``2 * shared / total`` plus ``exact`` (identical up to local names). The C/C++ reader takes one branch of every preprocessor conditional (the first, or the next after ``#if 0``) instead of all of them, and keeps a ``/* ... */`` comment spanning lines inside a ``#define`` part of the directive: on CPython's C sources the rejected files went from 17 to 1 (``Include/internal/pycore_fileutils_windows.h``, whose ``extern "C" {`` is never closed). In C/C++ only a declaration binds a local: an assignment to a member (``m_table = table`` vs ``m_where = clause``) keeps the member's name, so two setters of different members no longer compare exact; a ``/*`` inside a directive's ``//`` comment or quoted header name opens no comment. Names are resolved statically before comparing (``similarity/names.h``): Python imports, ``from ... import``, aliases, relative imports and module-level definitions become fully qualified names, scoped as Python scopes them (``os.path.join``, ``path.join``, ``osp.join`` and ``j`` after ``from os.path import join as j`` are one tree; ``builtins.len`` is ``len``; import statements inside units are dropped), and C++ namespace aliases and using-declarations do the same (``std::move``, ``::std::move``, ``using std::move; move``); ambiguous bindings, star imports, ``using namespace`` and runtime aliases stay as written. A module-level alias (``list = list``, ``getcwd = os.getcwd``) resolves to what it aliases. ``add(..., module=)`` / ``add_file(..., module=)`` name the module, ``add_file`` deriving it from the surrounding ``__init__.py`` packages. Classes pair their methods by maximum-weight assignment (Hungarian, exact integers). Python is read by ``pygim.code``'s parser in C++ (Python 3.14's grammar, whatever Python runs pygim), C/C++ by pygim's own tokenizer and bracket-structure reader (no compiler). The language registry is open — one header per language in ``src/_pygim_fast/similarity/adapter/languages/``, discovered by the build — and a ``corpus<L>`` only accepts what L's frontend parsed, so a cross-language comparison does not compile (``tests/static/similarity_proofs.cpp``); ``add_file`` refuses another language's file with ValueError. Large results: ``pairs(limit=N)`` keeps only the best N, each worker raising its own floor so most comparisons are never made (exactly the head of the full ranking); ``pairs()`` builds its ranking in batches of ``batch_size`` merged straight from per-block sorted parts at exact rank boundaries, never copying the whole; ``stream_pairs()`` returns an unranked ``pyarrow.RecordBatchReader`` swept on every core while it is read, in bounded memory, with batches identical for any thread count, failing (``ArrowInvalid``) if the index is added to meanwhile; every string column is dictionary-encoded and ``columns=`` selects the columns (``["a", "b", "score"]`` is 16 bytes a row). Measured on 72M pairs (4 cores): stream 1.5-2.6 s at ~400 MiB, top-1000 3.2 s at 32 MiB, full ranked table 4-12 s at 3.5-6.5 GiB. Results are identical for any thread count. CLI: ``pygim similar [PATHS] [-t THRESHOLD] [-k function|class] [-m MIN_SIZE] [-n LIMIT] [-x GLOB]``, one index per language found. The extension is ``pygim._similarity`` (links Arrow), re-exported by ``pygim.similarity``; datagen's Arrow stream exporter moved to the shared ``utils/arrow_stream.h``. Benchmark: ``benchmarks/similarity_sweep.py``. Design: ``docs/design/similarity.md``.

  How it was made fast:

  - a scored pair (``match``) is 24 bytes, not 32: its shared and total counts are 32-bit, since an index now holds at most 2^32 - 1 subtrees, every unit's together (``std::length_error``, ``ValueError`` from Python, past that; LLVM's functions hold 3.1M). Interleaved, ranking Lib/test's 62M class pairs 3.95-4.21 -> 3.29-3.30 s and its peak 5.9 -> 5.3 GB above the index. The same pairs.
  - a block of a megabyte or more that a query frees is kept for the next allocation of its size (``utils/kept_blocks.h``: ``kept_vector``, and ``unfilled_vector`` on it; sizes rounded up to eight steps between powers of two, at most 256 MiB kept, the oldest dropped first) instead of going back to the kernel and faulting in again page by page: a ranked query on CPython's Lib/test faulted 14,000 pages every run, and now about 100. Repeated queries 20-25% faster (Lib/test's top 200 30-32 -> 22-24 ms, LLVM's ranked query at 0.8 46-48 -> 37-39 ms). The token index's arrays and the sweep's pairs (``matches``) use it; ``tests/static/run_threads_stress.py`` drives it, with the parked pool, under ThreadSanitizer and AddressSanitizer.
  - ``pygim similar`` filters the files it walks by pygim's own paths (pathlib's ``relative_to`` took 0.4 s on CPython's Lib), sorts them as strings in pathlib's order, joins each side's ``qualname  file:line`` in Arrow's kernels instead of turning every dictionary value into a pyarrow scalar, and pads its table a column at a time: ``pygim similar Lib`` 0.86-0.91 -> 0.49-0.53 s, the output byte for byte the same (``test_the_printed_table_is_the_pairs_cell_by_cell``, for an absolute root and for ``.``).
  - what a corpus state gives every query is kept with the index until an ``add()``: the units' names, files and lines as the results' dictionaries (``tables::unit_columns``; built per query they took 25-30 ms of LLVM's ranked query, 16 ms of Lib/test's, on one thread) and each kind's sweep order (sorted per query: 10 ms on LLVM). Every result of an index shares one dictionary, as before; the qualname dictionary is interned with ``mapping::basic_hashed_interner`` (9-11 ms where an ``unordered_map`` took 11-18 ms). ``add_files`` reserves the corpus once. Interleaved, best of three on 16 threads, a repeated query: LLVM ranked at 0.8 84-88 -> 46-48 ms, its top 1,000 89-91 -> 48-50 ms; Lib/test ranked at 0.8 46-48 -> 30-31 ms, its top 200 44-47 -> 29 ms, its classes at 0.5 156-165 -> 144-149 ms; a first query 5-15 ms faster (``test_a_query_after_an_add_sees_the_added_units``).
  - class streams cut their work by what it costs — a row's methods times its partners', and 4 a pair (``class_costs``, fitted to Lib/test's 11,115 class rows timed one by one) — as well as by pairs: the heaviest classes come last in a sweep (Lib/test's last tenth of rows holds 1% of the pairs and 45% of the time), and blocks of equal pairs left a stream's end to a few blocks one worker each. At threshold 0 ``stream_pairs(kind="class")`` is placed as the function stream is: each pair written straight into its batch's columns at its place, in tiles of at most 1/64 of a worker's share, a heavy class's row cut into pieces for several workers (``place_tiles``, ``sweep_rows::counted_class_partners``, ``placed_class_law``), with no join of blocks on the reader's thread; with a threshold its blocks close at that share too (``class_sweep_blocks``). Through Python, with the assignment below: Lib/test's 62M class pairs 1,827 -> 1,154-1,161 ms (a, b, shared, total), 2,224-2,240 -> 1,272-1,276 ms (every column), at 0.5 424-433 -> 151-153 ms; the stdlib's 3.4M 162-165 -> 101-103 ms, at 0.5 62-63 -> 21 ms. The same batches (``test_the_class_stream_is_the_class_sweep_in_order``).
  - a class pair's method assignment reads its weights through an accessor — a class row hands over its tile of method counts; no matrix is copied a pair — into 32-bit costs in one pass that also finds each method's best partner (64-bit from a weight of 2^28 up), and its Hungarian numbers the columns from 0 and masks those it reached instead of branching on them. Its potentials stay within the largest weight and its reduced costs within twice it (argued in ``assignment_solver``); it is proven against enumeration on 400 seeded matrices with ties, hub columns, zero rows, and weights just under 2^28 and past 32 bits (``assignment_enumeration_law``). The stdlib's 744,955 class pairs that need the algorithm, one thread: 472-479 -> 416-432 ms; Lib/test's class rows on 16 threads 974-1,070 -> 854-925 ms; ``pairs(kind="class", threshold=0.5)`` of Lib/test 178-180 -> 143-159 ms. The same scores.
  - the token index — every unit's subtrees ranked by how many units hold them, each with its posting list — is built on every core, where only its sort was: five steps of tasks that touch disjoint data (``build_grain``, ``sequential_build`` / ``parallel_build``). The tokens are written straight into buckets of their hashes' top bits and each bucket is sorted by a radix pass; equal tokens' groups are ranked by a stable counting sort in two passes over whole groups; each row's prefix and each rank's rows are cut and gathered task by task. Its arrays are ``utils/unfilled.h``'s vectors, whose resize writes nothing, so their pages fault in on every core (on huge pages, 16 threads faulting at once took longer than one). The same index, array for array (``token_index_build_law``, and against the old build on LLVM and CPython's corpora). LLVM's 140,686 functions on 16 threads: 79-114 -> 44-57 ms at threshold 0.8, 124-144 -> 51-56 ms at 0; through Python, LLVM ranked at 0.8 114-144 -> 86-88 ms and its top 200 131-142 -> 89-91 ms, Lib/test's top 200 59-61 -> 42-45 ms.
  - ``pygim similar`` reads each language's files through ``Index.add_files`` — on every core, the GIL released — instead of ``add_file`` one by one, and prints its table itself, a column read at a time, instead of through tabulate (0.5 s for 23,000 rows): CPython's ``Lib`` 2.1 s -> 0.69 s, the whole checkout 3.4 s -> 1.3 s, the same pairs and the same skipped files. The score column is text in every section: three decimals, left-aligned (tabulate right-aligned it where no pair was exact).
  - a class pair whose methods' best partners alone cannot lift it to the floor is never assigned — the sum of the smaller side's best partners bounds every assignment — and where those partners are all distinct they are the assignment; the Hungarian algorithm keeps its buffers from pair to pair. The same rows. Interleaved on 16 threads: Lib/test's classes at 0.5 700 -> 203 ms, at 0.8 333 -> 122 ms; the stdlib's at 0.5 74 -> 29 ms; Lib/test's class stream 2.05 -> 1.81 s.
  - class pairs — ranked, or streamed — take their shared counts from two indexes of every token (the classes' own subtrees, and their methods class by class) instead of merging every method pair; only each pair's method assignment is computed. Counts are taken for tiles of partner classes sized to a worker's L2. With a limit too, since on most corpora the floor rises too slowly to cut many merges: the stdlib's top 2,000 432 -> 23 ms, its top 200 at 0.8 107 -> 8.5 ms; Lib/test's top 200, where exact copies raise the floor at once, 19 -> 28 ms. The same rows (proven at compile time, digests of every ranked and streamed class pair). Interleaved on 16 threads: Lib/test's classes at 0.5 3.1 s -> 0.70 s, at 0.8 1.18 -> 0.33 s; the stdlib's at 0.5 279 -> 75 ms; Lib/test's 62M class pairs streamed 11.3 -> 2.1 s.
  - the C/C++ reader asks what a token is by a one-byte word id (every keyword and punctuator numbered at compile time, ``detail::syntax_words``) instead of comparing its text — 124M text compares per pass over LLVM — and takes each syntax leaf's and literal type's atom from a table instead of hashing its text. A text the reader names that is no C++ word is now a build error. Units, pairs and every streamed row unchanged. One thread over LLVM (141 MB): parsing 1.24-1.26 s -> 0.92-0.94 s; ``add_files`` on 16 threads 277-281 -> 230-236 ms.
  - the ranked sweep's collectors ask Linux for 2 MB pages before they are first written (``utils/huge_pages.h``, ``prefer_huge_pages``: one page fault per 2 MB, not 512). With the token index's arrays, which asked too: top-200 of Lib/test 86-95 -> 67-69 ms, of LLVM 156-167 -> 131-147 ms; ranked at 0.5 of the stdlib 59-60 -> 49-53 ms. The index's arrays stopped asking once its build wrote them on every core (the entry above): 16 threads faulting 2 MB pages at once were slower than 4 KB pages (59 against 47 ms on LLVM). A no-op on other systems and under 4 MB.
  - ranked class pairs without a limit are swept a row at a time, heaviest class first, instead of in 32 blocks of equal candidate count — a class pair costs its method matrix, and the heaviest classes, last in the order, made one block the straggler. With the set intersections above, interleaved on 16 threads: Lib/test's classes at 0.8 16.5 s -> 1.19 s, at 0.5 42.6 s -> 3.08 s; the stdlib's at 0.8 1.14 s -> 0.11 s. A limit keeps the lightest first (their exact copies raise its floor at once). The same rows.
  - a fingerprint holds its subtrees as a set — a repeated subtree's k-th repeat stands as a value of its own — so the shared count of two units is the size of a set intersection (``utils/sorted_sets.h``), compared four values a step with AVX2 where the processor has it (chosen at run time; the branch-free merge otherwise and under constant evaluation). Results are unchanged (every unit, ranked pair and streamed row of CPython's corpora and LLVM identical). Measured interleaved on 16 threads: Lib/test's 62M class pairs streamed 16.2 s -> 11.6 s, ranked at 0.5 336-345 -> 307-317 ms, the C core's 38.6-39.5 -> 33.2-34.6 ms.
  - ``stream_pairs()`` of functions at threshold 0 — every pair kept — writes each pair straight into its batch's Arrow columns at its place in the sweep, in tiles sized to a worker's L2 cache, with at most an eighth of the L3 in flight ahead of the reader: no collector of records, no copy and no join of blocks into batches. Every streamed row is unchanged (digests over CPython's 1.27 billion function rows, its class streams and thresholded streams).   - Python is read by pygim.code's C++ parser (Python 3.14's grammar, whatever Python runs pygim) instead of walking the interpreter's ``ast`` through the C API — the same units and pairs on CPython's corpora but for type parameters' 3.13 ``default_value`` field. ``Index.add_files(files, *, threads=None)`` reads, parses and fingerprints on worker threads with the GIL released and Ctrl-C owned, then adds the units in the given order (ids as ``add_file()`` in a loop), returning ``(path, message)`` for each file left out. ``pairs()`` of functions at a threshold >= 0.5 compares only units whose prefixes of rarest subtree occurrences share one (an exact prefix filter); ``pairs(limit=N)`` tries that filter at falling thresholds until one finds N pairs; streams and the remaining sweeps read shared counts from an index of every token instead of a merge per pair; a subtree is its 64-bit Merkle hash and the merge is branch-free; a stream's workers build their blocks' Arrow columns.   Settled before it shipped:

  - ``Index.add_file(path)`` reads the file in C++ (pathlike's ``file_reads.h``) and parses and fingerprints it with the GIL released, instead of ``io.open()`` and ``os.fspath()`` imported on every call: a FIFO is an ``OSError`` at once instead of a read that waits for a writer forever; other errors are the ``OSError`` subclasses ``open()`` raises, and a source that does not parse is still ``ValueError``.
  - ``pygim similar`` given one tree twice — as an absolute and a relative path — reads each file once, by its first spelling, where every function paired with its own copy; ``-x`` leaves out a file named on the command line too; a root that is neither file nor directory (a FIFO) says so; with ``-n`` the header says ``the best N`` pairs, not N in all; ``--check`` exits 1 when it shows any pair, as a gate in CI.
  - the Python frontend resolves a function's defaults and decorators, and a class's bases, keywords and decorators, where Python evaluates them — in the scope around the definition — not in the definition's own: in ``def f(a, x=x)`` the default was the parameter, renamed, so it matched ``def g(a, z=z)`` and not ``def g(a, y=x)``. A walrus in a decorator now binds in the enclosing function as its other statements do. 31 of CPython's 74,592 stdlib and Lib/test units change (``copy._deepcopy_list(x, memo, deepcopy=deepcopy)`` and the like); no ranked pair at 0.8 does.
  - the C/C++ reader misread what the review found (2026-10-29). A name after `>`, `&`, `&&` or `not` in a condition or a call's arguments was taken for a declared local and renamed, so functions masking or comparing with different globals (LLVM's `Flags & innerLoopMask` and `& outerLoopMask`) were exact copies; a name binds only after a type where declarations are read, and `map<K, vector<V>> m` binds `m`. ``final``, ``override``, ``import`` and ``module`` are names, so a C parameter named ``module`` is renamed. ``struct alignas(16) S {...}``, ``inline namespace v1 {...}`` and ``class LLVM_ABI Foo`` give their classes and functions (lost, or named after the macro); ``#elifdef`` and ``#elifndef`` choose a branch; a ``//`` comment ending in ``\`` goes on to the next line, and a string spliced by ``\`` before ``\r\n`` reads. On LLVM 156,089 units became 156,334 (classes named after export macros renamed, classes behind ``alignas`` and interface macros found); on CPython's C, 84 exact pairs that reference different globals are no longer exact. In the Python frontend, a method defined under a statement of a class body (``if _mswindows: def _get_handles``) was in the class's own tree too. A fingerprint whose repeat collides with another subtree takes the next free repeat number, so it stays a set and the AVX2 merge counts what the others count. ``split_name`` with an empty separator returns the name instead of looping.
  - ``len()``, ``stats()`` and ``repr()`` of an ``Index`` while ``add_files()`` grows it on another thread read the corpus under its lock instead of walking units being moved (a segfault), and a class ``stream_pairs()`` at threshold 0 counts each tile's rows under the lock too (ThreadSanitizer reported its race with ``add()``). A stream's workers are ``std::jthread``\ s, stopped and joined even when starting them fails; a stream read in a forked child fails at once instead of waiting for workers left in the parent.
  - ``add_files()`` names each file it leaves out and says why in the OS's words (``<path>: No such file or directory``, ``Is a directory``, ``Permission denied``; ``not a regular file`` for a FIFO or a device), where a missing file and a directory both said ``not a regular file`` and a refused read named no file — so ``pygim similar``'s ``skipped:`` lines name them too.
  - a ``batch_size`` past every count — ``2**64 - 1`` — is one batch of everything; counting batches as ``(pairs + batch_size - 1) / batch_size`` wrapped to none (``utils/pieces.h``).
  - ``src/pygim/similarity.pyi`` stubs ``add_files()`` and ``__repr__``; a test holds every method's parameters to the binding's.
  - ``pairs(limit=N)`` of 4,096 functions or more kept every pair each threshold of its ladder found until the end — 12,000 identical functions held all 72M pairs at 1.0 (3.2 GiB, 1.7 s) to return 1,000. Each worker now keeps only its best N, admitting against its rising floor: 7 MiB and 0.3 s, the same rows.
- Code: ``pygim.code`` parses Python 3.14 in C++. ``code.parse(root, "**/*.py", *, threads=None)`` walks, reads and parses a whole tree in one run on a task pool, with the GIL released and Ctrl-C owned, and returns a ``Corpus``: the files sorted by path, each a syntax tree or the reason it is not one (``corpus.errors``; ``corpus[path]`` raises its ``SyntaxError``), with one name table for all of them. ``code.parse_source(str or bytes)`` parses one text. ``Tree`` and ``Node`` are views: ``node.kind``, ``node.field(name)`` (what ``ast`` holds: a node, a list, a name, a constant's value, operators and contexts by name), ``parent``, ``children``, ``lineno``/``col_offset``/``end_lineno``/``end_col_offset``, ``source``, ``tree.find(kind)``, ``tree.kind_counts()``. ``dump(include_attributes=)`` writes exactly what Python 3.14's ``ast.dump`` writes; node kinds and fields are generated from its ``ast`` module. A hand-written parser after Ruff's layering (#280): a lexer read one token ahead, statements, expressions by operator strength, patterns; each node becomes a row as it closes and one reverse pass puts a file's rows in source order, so nothing is built to be thrown away. Checked against CPython: CPython 3.14.3's ``Lib`` (1,846 files) dumps the same with positions but for 4 files, 2 with NFKC identifiers and 2 only in ``repr``'s Unicode version; 52,000 token-level mutants and 8,750 code strings from CPython's tests are accepted or refused as CPython does but for one unknown ``\N{NAME}``. Measured: 355 ms on one thread for that ``Lib`` (36 MB), 75 ms for the whole run on 16 threads, against 4.2 s for ``ast.parse``. Not yet: multi-byte encodings; NFKC; error recovery and CPython's wording of most errors; versions before 3.14. Design and decisions: ``docs/design/code_parser.md``; example: ``docs/examples/code/example_01_parse_a_tree.py``; oracle: ``benchmarks/code_oracle.py``.

  How it was made fast:

  - each file is read into its worker's chunks, and its tree's nodes, text and lines are kept there (``utils/chunk_arena.h``: 4 MB at a time from the process's kept blocks, handed out by a pointer bump, given back with the corpus), so a fresh process's first ``code.parse`` no longer pays for the C library's per-thread heaps growing 128 KB a step: 17.9-23.8 ms on python3.14's library, against 31.4-33.4 with everything on the heap and 25.3-30.1 with the texts still there; 74-103 against 132-148 and 101-121 on a python3.12 library; later runs unchanged (D61, D69).
  - ``code.parse(threads=None)`` parses on one thread per core from the start (Q39): CPython's ``Lib`` in 76-77 ms, where the elastic width took 140-150 ms; pathlike's reads keep growing their width while more threads help.
  - ``code.parse`` renumbers the files' trees into the corpus's name table on every core, and a node's kind says from a compile-time table whether it holds an identifier (each node walked its kind's fields): the merge after a run 27-29 -> 13-14 ms, ``code.parse`` of CPython's Lib on 16 threads 77-79 -> 60-62 ms. ``parallel::for_each`` and ``workers_for`` moved from similarity's adapter to ``utils/parallel.h``, one loop for both.
  - a source's line starts come from one 64-byte mask per 64 bytes, every line end taken from it (``byte_scan::for_each_line_end``), instead of a search per line, and the whole-buffer scans compare 32 bytes at a time with AVX2 where the processor has it (chosen at run time; SSE2 and NEON otherwise). On CPython's Lib, one thread: the line index 12.6-13.5 -> 3.9-4.4 ms, ``code.parse(threads=1)`` 425-428 -> 408-412 ms.
  - the source checks that read a whole buffer — is it UTF-8, where do its lines start — scan 64 bytes a step at 128-bit width (``utils/byte_scan.h``: SSE2 on x86-64, NEON on arm64, the scalar loop the definition): 33 ms -> 10 ms for CPython's ``Lib``.

- Utils/PathLike: a native run owns Ctrl-C and SIGTERM while it lasts, with no Python and no polling (``utils/interrupt.h``, ``interrupt_scope``). A signal the program ignores is left alone. - PathLike: ``PathSet.read_each(*, threads=None, ahead_bytes=64 MiB)`` hands over each member's contents in member order while C++ threads read the next files with the GIL released, so the disk and the caller's code work at the same time. Each item is a ``FileContent``, a view of bytes held in C++: ``memoryview(content)`` copies nothing (``zlib.crc32(content)``, ``hashlib`` and other buffer readers take it as it is), ``bytes(content)`` copies, ``text()`` decodes UTF-8 and ``.path`` is the member. The width: the caller reads alone at first, and each finished file may add threads while the rest is worth more than the ~20 µs a thread costs to start — up to the cores for reads that compute (a warm cache) and up to max(32, 2 x cores) for reads that wait (a cold disk, a network mount), told apart by sampling each thread's CPU clock; ``threads=n`` fixes it. Experiments and rejected shapes (separate reader and CPU stages, mmap, read-ahead hints, a probe of the first files, throughput feedback, a small window): ``docs/design/pathset_storage.md``.
